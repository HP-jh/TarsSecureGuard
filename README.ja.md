## 🌟 紹介文

TarsSecureGuard は**ローカルファースト（local-first）の AI ゲートウェイ——AI 時代のルーター**です。ユーザーとすべての AI 機能の間に位置し、左側にはお使いの AI ソフトウェア（Claude Desktop、Cursor、Cline、Windsurf、Codex CLI……自由に選択可能）、右側には 24 社のクラウドモデルベンダー + 8 種類のローカル推論ランタイム（自由に接続可能）を接続；外部に OpenAI 互換エンドポイント（HTTP または **stdio**）+ MCP を公開し、内部で統一的なスケジューリング、統一的なガバナンス、統一的な監査を実施します。

> 家庭用ルーターは LAN ケーブルを生産したりウェブサイトを運用したりしません——各端末が安全にインターネットに接続できるようにするものです。TarsSecureGuard はモデルを生産したり特定のクライアントの使用を強要したりしません——**各 AI クライアントがすべてのモデルを安全に利用できるようにするものです**。この目標を極限まで追求します：接続できるものは接続し、一時的に接続できないものには実行可能な接続手順リストを提供します（`docs/v3.2.0-unconnectable.md` を参照）。

### v3.2.0 新機能 · Universal Connector ロードマップ

> **Coding Plan サブスクリプションキー 1 つ = すべてのモデルへのアクセスキー**。TSG が各プロバイダーの差異を OpenAI 互換レイヤーの背後に隠蔽するため、AI クライアントの書き換えは不要で、ユーザーがツールを切り替える必要もありません。

世界中のすべての AI ソフトウェア（直接接続できないオープンソース / クローズドソース / CLI ツールを含む）を TSG に取り込むための 3 種類の**取り込みモード**：

| モード | 対象 | 方法 |
|---|---|---|
| **embed（埋め込み）** | オープンソースライブラリ（C/C++/Go/Rust/Python）| コードを TSG プロセス内にコンパイルして直接呼び出し（例：ggml / whisper.cpp / sqlite-vec）|
| **federate（フェデレーション）** | リモートサービス / API ゲートウェイ | TSG のリバースプロキシ + プロトコルアダプターで統一的にスケジューリング（各社 MCP Hub、第三者 API プラットフォーム）|
| **wrap-cli-as-mcp（CLI を MCP としてラップ）** | 任意のコマンドラインツール | コード不要で MCP サーバーとしてラップし、AI が TSG 経由で間接的に呼び出し（例：ripgrep / fd / magika / jq）|

**現在の進捗**：24 社のクラウドプロバイダー + 8 種類のローカルランタイム（内蔵登録済み、各社ごとに機械可読なプロファイルを用意）、13 種類のクライアント接続ガイド、17 項目の一時的に接続不可能なリスト（v3.3.0 で 50 個のインテグレーションを目標）。**新規プロバイダー追加時は設定のみでコード変更不要**——これが v3.2.0 が「ルーター」の役割を担える理由です。

## 🧩 v3.0.0 機能一覧（"Your AI's Safety Belt"）

### A ライン · リソースガーディアン（resourceGuardian）
- `GOMEMLIMIT` ソフトメモリ上限（min(物理メモリの 10%, 384MB)、eco モードでは 128MB、上書き可能）。
- **L0–L3 段階的応答**：L1 非コア機能の縮退 → L2 高負荷機能のサーキットブレーカー → L3 正常なシャットダウン（30 秒間のドレイン + 監査データのディスク書き込み + 状態の保存 + 終了コード 42 + クーリングによるストーム防止）。
- L2/L3 は **RSS 基準** で判定し、CGO / 外部メモリリークを捕捉；eco 省リソースモードはローエンドハードウェアに対して自動的に適用されます。

### B ライン · 保護の強化
- **意味的検出による段階的なトラフィック分岐（semanticGuard）**：まず静的ルールで判定し、グレーゾーンのコンテンツはローカルの 0.5B–1.5B の小型モデルで判定；**fail-close の原則**——エンジンが使用不能な場合は直接 503 を返し、絶対に通過させません；指紋キャッシュ + グレーゾーンのレート上限を実装。
- **3 次元トークンバケットレート制限（rateLimiter）**：IP×エンドポイント種別 / キー×エンドポイント種別 / IP 全体の 3 次元で制限、超過した場合は 429 を返して評価スコアの減点と連動します。
- **ローカル IP 評価（ipReputation）**：初期スコア 100、WAF 検出 / スキャン行為 / レート制限超過で減点、低スコアは自動的に BAN、ホワイトリスト機能、24 時間で自動回復、NAT 異常アラート、管理者による BAN 解除機能を備えます。
- 「**AI は常に制限を強化する方向でのみ動作する**」単方向マージの原則：セキュリティポリシーはより厳格にすることのみ許可され、100% の単体テスト + 実行時監査を実施します。

### C ライン · 2 段階スマートルーティング
- **smartRouter**：静的ルールを優先的に適用 + **ε-greedy バンディットアルゴリズム**（ε を 0.1 から 0.02 に減衰）、成功率/レイテンシの履歴に基づいて自動的に最適なバックエンドを選択；管理者以外のフィードバックは重みを下げて偽造を防止します。
- **scoreBoard**：実行時スコア（成功率×レイテンシ）と **lm-eval-harness** のオフライン評価結果を融合（相対的な参考値、正直なラベル付け；Python サイドカーは必要に応じて使用し、バンドルはしません）。

### D ライン · エコシステムの次元上昇
- **`--mcp-stdio`：stdio 上での JSON-RPC 2.0 サポート**、任意のローカルエージェントを接続するだけで全機能の保護を利用可能——本バージョンのコアな差別化機能です。
- ツール：`tars_guarded_chat` / `tars_guard_status` / `tars_route_preview` / `tars_model_score` / `tars_module_schema` / `tars_ip_reputation_unban`；管理操作には `TSG_ADMIN_KEY` が必要で、全行程が監査されます。

### E ライン · 安定性エンジニアリング
- panic recovery を全範囲に適用；Go fuzzing（WAF / 設定パース / 意味的正規化）を実施；**8 時間の soak 負荷テストスクリプト**（`soak.sh` / `soak.ps1`）を用意；単体テスト + httptest 統合テストを `-race` オプション付きで実行し全て合格。

### プラットフォームとデリバリー
- UI は完全日本語化済み；**展開用ファイルを完備**：systemd ユニット、Dockerfile、docker-compose（rootless）、K8s sidecar の例、macOS LaunchDaemon（[`deploy/`](./deploy) を参照）。
- `go.mod` に第三者依存関係がなく、全て標準ライブラリを使用——**サプライチェーン攻撃のリスクがゼロ**です。


### UI アップグレード（v3.2.4）
**ガバナンス層のフロントエンド可視化**：サイドバーに「ガバナンス」ナビゲーショングループを追加、ガバナンス概要（統合ガバナンス+OAuth 状態）/ 共有メモリ / 共有情報 / 監査チェーン v2 の 4 ページ全てが実際の API と接続——以前はガバナンス関連の 8 つの REST エンドポイントはフロントエンドからアクセスできず、curl でのみ操作可能でした。監査ログのエクスポートは認証ヘッダー付きの blob ダウンロードを使用（キーが URL に記載されません）；さらに v3.2.2 以降発生していたサイドバーのバージョンバッジの位置ずれを修正しました。Playwright + Chromium のヘッドレス E2E テストに全合格、フロントエンドに特権はなく、監査の視野を緩めていません。詳細は [docs/v3.2.4-ui.md](./docs/v3.2.4-ui.md) を参照。

### パフォーマンスアップグレード v2（v3.2.3）
**WAF の単一パス結合正規表現 + ASCII トリガーバイトの事前スクリーニング**（normal/strict モードそれぞれ 1 本の結合正規表現で単一パスの高速スクリーニングを実施、ヒットした場合にルール名を逆引きするため意味的な変化はなし；純中国語の本文全体は正規表現のチェックをスキップするため、strict モードのスキャン時間が -99.8% 削減）、**PII マスキングの単一パス化**（4 つのモードを 1 回の置換処理に統合、-15% 削減）、**応答キャッシュの 16 シャードロック**（FNV-1a でシャードを決定、独立した mutex+LRU を使用、2 コア環境での並列 get/put 処理が -10% 削減）——候補となる施策を 1 つずつ検証して決定：JSON sync.Pool と監査のバッチコミットは除外（書き込み順がハッシュチェーンの順序と一致する必要があるため、非同期化するとチェーンが切断されるリスクがある）、SSE パスは存在しないことを確認。詳細は [docs/v3.2.3-performance.md](./docs/v3.2.3-performance.md) を参照。

### ガバナンス層 + パフォーマンスアップグレード v1（v3.2.2）
**共有メモリ**（user → tenant → global の 3 層ネームスペース、近い階層から順に上書きする解決チェーン、テナント分離はネームスペースの正規化によって保証）、**共有情報**（fact/preference/note/link の構造化知識エントリ + 重み付き検索）、**コンテキスト拡張 MCP**（ID とポリシー + 共有情報 + 共有メモリを組み合わせて確定的なコンテキストパッケージを組み立て、注入されるコンテンツはユーザー入力と同じセキュリティチェーンを通過）、**OAuth/OIDC 企業 IdP 接続**（Authorization Code + PKCE、標準ライブラリで手書きした RS256/ES256 検証を使用、fail-close、セッションはローカルユーザーと完全に同一の RBAC マトリクスを適用）、**ゲートキーパー**（ツール実行前のアクションレベルの防衛ライン：セキュリティ設定の変更禁止、機密パスへのアクセス禁止、高リスク操作の 2 段階確認、ID 注入の偽造防止、制限強化のみ許可する設定）、**hash-chain 監査 v2**（前後のチェーンは SHA256 でハッシュ化、日ごとにファイルを分割、再起動時にチェーンを再開、全チェーンの再計算による改ざん防止）——詳細は [docs/v3.2.2-governance.md](./docs/v3.2.2-governance.md) を参照。また**パフォーマンスアップグレード v1** も含まれます：常時オープンのログハンドルパイプライン（1 行あたりのディスク書き込み時間が -79% 削減）、接続プールのカバレッジ補完（doctor 検出のプール化 / customToolClient のパラメータを統一しつつ SSRF 分離を保持）、tier1 正規表現のパッケージレベルでの事前コンパイル——詳細は [docs/v3.2.2-performance.md](./docs/v3.2.2-performance.md) を参照。

## 🥊 最大競合他社分析

**結論：現在最大かつ最も正面から対応すべき競合は LiteLLM です**（オープンソース AI ゲートウェイの事実上の標準、約 6 万 Star、エコシステムと認知度が最も高い）。国内市場では **New API / One API** が Go 技術スタックの認知リーダーであり、「ローカル優先」の定位では **OmniRoute** が最も近い位置にあります。

| 競合 | 強み | TarsSecureGuard と比較した短所 |
|------|------|----------------------------|
| **LiteLLM**（最大の競合） | プロバイダーの対応範囲が最も広くエコシステムが成熟、仮想キー/予算/リトライ機能が充実、海外での認知度No.1 | Python 技術スタックのためデプロイが重い（Postgres + Redis が必要、イメージサイズ 500MB+ で全体で 1GB 近く）；クラウドモデル中心の設計；セキュリティがデフォルトの訴求点ではない；単一ファイルで解凍してすぐに使えない；意味論的な fail-close / リソースガード機能がない |
| **New API / One API**（国内での認知が高い） | Go で開発、国産モデルへの対応が充実、チャネル/トークン/課金/チャージの運用フローが完備 | 「API 転売/運用課金」を定位としており、MySQL + Redis が必要；パラメータが複雑；ローカルモデル/スタンドアロンのセキュリティシナリオ向けに設計されていない |
| **OmniRoute**（ローカル優先） | local-first の定位が明確、Star の増加が速い、自動フェイルオーバーと複数のルーティング戦略を備える | 「マルチベンダー集約ルーティング」に偏っており、セキュリティガバナンス（WAF/意味論/RBAC/レート制限/IP レピュテーション/監査/PII）がコア機能ではない；単一ファイル・ゼロ依存でのイントラネットコンプライアンスを主張していない |
| **LM Studio / Ollama + OpenWebUI**（「十分な機能」の代替品） | ユーザーが既に導入している可能性が高く、GUI が使いやすい、モデルの検索が容易 | これらは**ランタイム**でありガバナンスゲートウェイではない：WAF、意味論的防御、レート制限、IP レピュテーション、RBAC、監査、リソースガードを提供していない —— TarsSecureGuard はこれらを統合管理してこのレイヤーを補完する |

**差別化戦略**：「プロバイダーの対応数」で争うのではなく、個人やイントラネットにとって看過されてきた非常に痛みの大きいニッチを獲得する —— **「ゼロ設定 + 単一ファイル + セキュリティデフォルト有効 + ローカル優先 + stdio プラグアンドプロテクト」**。重量級ゲートウェイはプラットフォームチームを持つ大企業向けのサービスであるのに対し、TarsSecureGuard は「今日すぐにローカル AI を安全かつ安定的に使いたい」個人、ギーク、隔離されたイントラネット環境向けのサービスです。

## 🏰 最も深い堀（競争優位）分析

**結論：最も深い堀は「Security Core」が蓄積してきた信頼資産と LLM セキュリティ防御ナレッジベースであり、「ゼロ依存単一ファイル」の攻撃表面ゼロのエンジニアリングにより持続的に強化されている。v3.0 の MCP stdio によりこの防御機能が接続と同時に自動的に配布され、堀はさらに拡大する。**

堀は浅い順に3層に分かれます：

1. **エンジニアリングの簡素さレイヤー（複製容易、短期的な優位性）**：サードパーティ依存ゼロ、純静的単一ファイル、6プラットフォーム対応、リソースガードとインテリジェントルーティング。競合が模倣することは可能だが、長期的に機能を抑制しエコシステムを放棄する必要があり、大半のチームには実現できない。

2. **セキュリティナレッジレイヤー（コアとなる障壁、時間とともに複利で成長）**：Security Core は**LLM に特化した防御資産**の一式である —— WAF とプロンプトインジェクション/ジェイルブレイクの特徴、意味論的なグレーゾーン判定（fail-close）、IP レピュテーションの行動フィンガープリント、3次元レート制限、PII パターンとデータマスキング、SSRF 5つのレッドライン、ファイアウォール連携、監査体系、さらに「検出率 vs 誤報率」の持続的なチューニングが含まれる。**実サンプルが多いほど → ルールが高精度になる → 誤報が減る → ユーザーが増える → サンプルがさらに増える**という自己強化型のフライホイールが形成され、後発者は一度コードをコピーしただけでは補完できない。

3. **信頼と配布レイヤー（最も深く、複製が最も困難）**：セキュリティ製品の最終的な障壁は**「一度も事故を起こしたことがない」という信頼記録**とコンプライアンスの認知であり、「セキュリティは永続的に無効化できない / AI の制限は常に強化方向にしか調整できない」という設計上の約束がデフォルトの選択として定着する。v3.0 の **stdio プラグアンドプロテクト**は、あらゆるローカルエージェントが接続するだけで防御機能一式を継承できることを意味し、防御能力が接続に伴って自動的に拡散する**配布フライホイール**が形成される。サブスクリプション版は持続的なセキュリティアップデートと SLA により信頼を収益化する。信頼は四半期ごとの短期間で構築できるものではなく、価格競争で破壊されるものでもない。

> **正直な評価**：プロジェクトは成長期にあり、競争優位は現在も「拡大中」であり、機能レベルでは複製可能である。真の優位性の幅は**導入量がもたらす防御データ + stdio 配布フライホイール + 長期的な無事故信頼記録**によって決まる。サブスクリプション版の戦略的価値はまさに、「持続的なセキュリティアップデート」を複利で成長し、課金可能で、信頼を蓄積できる資産にすることにある。
