## Round 4 — LLM 강화 페이로드(Agnes AI flash + 수동 협업)

LLM 첫 호출 성공으로 일반 페이로드 5개를 획득; 이후 요청 제한(429/403)으로 "LLM이 아이디어 키워드 제공 + 인간이 타겟에 맞춰 구성"하는 협업 모드로 전환:

| payload | 기법 | 블루 WAF 결과 |
|---|---|---|
| `UNION ALL SELECT NULL` | LLM 출력 | **401 WAF 우회**(\bunion\s+select\b가 UNION ALL SELECT와 매치되지 않음) |
| `1 /*!50000UNION*/ /*!50000SELECT*/ NULL` | MySQL 인라인 코멘트 | **401 WAF 우회** |
| `1%2520UNION%2520SELECT%2520NULL` | 이중 URL 인코딩 | **401 WAF 우회** |
| `1&id=1 UNION SELECT NULL` | HPP 매개변수 오염 | 403 차단 |
| `1 UNION SELECT 0x68656c6c6f` | 16진수 문자열 | 403 차단 |
| `1 UNION SELECT CASE WHEN(1=1) THEN 1 END` | CASE WHEN | 403 차단 |

**핵심 인사이트 #4(최대 발견)**: 블루팀 sqli 정규식은 `\bunion\s+select\b`로 UNION/SELECT가 **인접**해야만 매치되도록 강제한다. MySQL 인라인 코멘트(`/*!...*/`), ALL 추가, 이중 URL 인코딩 세 가지 방법 모두 UNION과 SELECT를 분리시킬 수 있음 → 3/6 우회 성공. 프로덕션 환경에서 WAF는 코멘트/인코딩을 파싱하고 모든 동등한 형태를 매치할 수 있어야 하며, 그렇지 않으면 차단하지 않은 것과 마찬가지다.

**Round 4 워크플로우 교훈**: LLM 할당량이 순식간에 소진되므로, 프로덕션 현실에서 AI 어시스턴트는 **자동 공격기**보다 **아이디어 생성기**로 사용하는 게 더 안정적이다 — "LLM이 방향을 제시하고 인간이 깊이 있게 타겟에 맞춰 구성"하는 방식이 더 효과적이다.

## Round 5 — 종합 공방 + 심층 방어 결함

| 벡터 | 블루 | 레드 |
|---|---|---|
| 경로 탐색(3종) | 3/3 차단 | 3/3 차단 |
| XSS `<script>` | 403 차단 | 403 차단 |
| XSS `javascript:` | 403 차단 | 403 차단 |
| XSS `<img src=x onerror=>` | 403 차단 | **404 누락**(WAF 매치 안됨) |
| cmd `;id` / `\|ls` / `` `id` `` / `&whoami` | 404(WAF 매치 안되지만 hello가 cmd를 받지 않음) | **401 누락**(WAF 매치 안됨) |
| UA 블랙리스트 전체 | `sqlmap/nmap/masscan` 차단, `Mozilla/5.0 sqlmap` 누락 | **전부 누락** |

**핵심 인사이트 #5(레드팀 XSS 취약점)**: 레드팀 xss 규칙을 `<script|javascript:|onerror=`로 작성할 때 `onerror=`를 **정확한 문자열**로 매치했지만, `<img src=x onerror=alert(1)>`에서 onerror= 뒤에는 `alert`이 붙어 유효한 이벤트가 아님 — 정확한 문자열 매치 대신 대소문자를 구분하지 않는 정규식 `onerror\s*=`을 사용해야 한다. 커버리지가 불충분하다.

**핵심 인사이트 #6(레드팀 cmd_injection 가짜 규칙)**: 레드팀 cmd_injection 규칙에 `;|\||\`|\&` 4개 문자가 나열되어 있지만, URL에서 `;`는 매개변수 구분자이고 `|` `&`는 쉘 연산자로, 이 문자들은 단독으로 나타날 때 **합법적인 URL 문자**다. WAF가 단일 문자로 매치하면 → 오탐률이 높아짐 → 규칙을 수정할 때 **의도치 않게 무효화될 가능성**이 있다. 검증에서 4개 페이로드 모두 401(WAF 우회)이 반환되었고, 블루팀 역시 4개 모두 404(마찬가지로 WAF 우회) — **양측의 cmd_injection 규칙이 실제로는 모두 무효**이며, `/api/hello`가 cmd 매개변수를 받지 않아 문제가 드러나지 않았을 뿐이다.

## 최종 평가: 핵심 보안 인사이트(프로덕션 적용 가능)

1. **인증 = 열쇠**: WAF는 "합법적인 인증 + 합법적인 경로"의 합법적인 접근을 막을 수 없다. 프로덕션에서 secret 인터페이스는 반드시 **추가 레이어**(IP 화이트리스트, mTLS, 동적 token, 요청 제한)를 적용해야 한다.
2. **WAF는 공격 특징을 정확한 문자열로 매치하면 안 된다**: `Mozilla/5.0 sqlmap` 누락, `<img onerror=>` 누락, UNION 코멘트 간격 우회 — 모두 "막은 것 같지만 실제로 막지 않은" 사례다.
3. **WAF는 반드시 header_anomaly를 포함해야 한다**: 레드팀의 4개 카테고리 규칙에 **UA 블랙리스트가 없어서** 어떤 도구 지문도 통과할 수 있으며, UA만 위장하면 된다.
4. **cmd_injection 단일 문자 규칙은 함정이다**: 잘못 작성하면 없는 것과 마찬가지다. 컨텍스트(명령 뒤에 오는 함수명 `id` `whoami` `cat` 등)와 결합하여 패턴 매치를 해야 한다.
5. **LLM은 어시스턴트지 대체재가 아니다**: flash 모델이 첫 호출에 성공했지만 이후 429/403 요청 제한이 발생 — 프로덕션에서는 반드시 "AI + 인간"이 협업해야 하며, LLM 공격에 완전히 의존해서는 안 된다.
6. **동일한 소스 코드는 동일한 취약점을 가진다**: 두 서비스의 기본 WAF 코드가 거의 똑같다는 점은 양측 모두 상대방과 같은 누락이 존재하며, 트리거 조건만 다르다는 의미다. 실제 생태계에서는 이것이 "41곳의 취약점 복제"로 이어진다.
