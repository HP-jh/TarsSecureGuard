## ラウンド 4 ― LLM 強化ペイロード（Agnes AI flash + 人手との協働）

LLM の初回呼び出しは成功し、一般的なペイロードを 5 件取得。その後レート制限（429/403）が発生したため、「LLM が方針キーワードを出力 + 人間が狙いを定めて構築」の協働モードに切り替えた：

| ペイロード | テクニック | 青 WAF の結果 |
|---|---|---|
| `UNION ALL SELECT NULL` | LLM 出力 | **401 WAF 回避成功**（`\bunion\s+select\b` が UNION ALL SELECT にマッチしない） |
| `1 /*!50000UNION*/ /*!50000SELECT*/ NULL` | MySQL インラインコメント | **401 WAF 回避成功** |
| `1%2520UNION%2520SELECT%2520NULL` | 二重 URL エンコーディング | **401 WAF 回避成功** |
| `1&id=1 UNION SELECT NULL` | HPP パラメータ汚染 | 403 遮断 |
| `1 UNION SELECT 0x68656c6c6f` | 16 進数文字列 | 403 遮断 |
| `1 UNION SELECT CASE WHEN(1=1) THEN 1 END` | CASE WHEN 構文 | 403 遮断 |

**核心インサイト #4（最大の発見）**：青チームの sqli 正規表現は `\bunion\s+select\b` を使用し、UNION/SELECT が**隣接**していることを強制している。MySQL インラインコメント（`/*!...*/`）、ALL の挿入、二重 URL エンコーディングの 3 種類の手法で UNION と SELECT の間に文字を挿入可能 → 6 件中 3 件で回避成功。本番環境の WAF はコメントやエンコーディングを解析し、すべての等価形式をマッチできる必要があり、そうでなければ防御していないのと同じである。

**ラウンド 4 ワークフローの教訓**：LLM のクォータは瞬時に枯渇する。本番環境で AI アシスタントは**アイデア生成器**として使用し、**自動攻撃器**として使用するべきではない――「LLM が方向性を示し、人間が深く対策を講じて構築する」方がはるかに安定する。

## ラウンド 5 ― 総合攻防 + 深層的な欠陥

| ベクター | 青 | 赤 |
|---|---|---|
| パストラバーサル（3 種） | 3/3 遮断 | 3/3 遮断 |
| XSS `<script>` | 403 遮断 | 403 遮断 |
| XSS `javascript:` | 403 遮断 | 403 遮断 |
| XSS `<img src=x onerror=>` | 403 遮断 | **404 検知漏れ**（WAF がマッチしない） |
| cmd `;id` / `\|ls` / `` `id` `` / `&whoami` | 404（WAF がマッチしないが、hello エンドポイントが cmd を受け付けない） | **401 検知漏れ**（WAF がマッチしない） |
| UA ブラックリスト全件 | `sqlmap/nmap/masscan` は遮断、`Mozilla/5.0 sqlmap` は検知漏れ | **すべて検知漏れ** |

**核心インサイト #5（赤チーム XSS 脆弱性）**：赤チームの xss ルールは `<script|javascript:|onerror=` を使用し、`onerror=` を**完全文字列**でマッチさせているが、`<img src=x onerror=alert(1)>` では onerror= の後に `alert` が続くため正しいイベントとして判定されない。完全一致ではなく、大文字小文字を区別しない正規表現 `onerror\s*=` を使用するべきであり、現在のルールはカバー範囲が不足している。

**核心インサイト #6（赤チーム cmd_injection の偽ルール）**：赤チームの cmd_injection ルールは `;|\||\`|\&` の 4 文字を対象としているが、URL 内で `;` はパラメータ区切り文字、`|` `&` はシェル演算子であり、これらの文字が単体で出現する分には**正当な URL 文字**である。WAF が単一文字でマッチさせる場合 → 誤報率が高くなる → ルール改変時に**意図せず無効化される可能性がある**。検証で 4 つのペイロードがすべて 401 となり（WAF 回避）、青チームも同様に 4 つすべてが 404 となった（同様に WAF 回避）――**両チームの cmd_injection ルールは実質的に機能していない**が、`/api/hello` が cmd パラメータを受け付けないため問題が表面化していなかっただけである。

## 最終評価：コアセキュリティインサイト（本番環境に移植可能）

1. **認証情報 = 鍵**：WAF は「正当な認証情報 + 正当なパス」による正規アクセスを遮断できない。本番環境では secret インターフェースに**必ず追加の防御層**（IP ホワイトリスト、mTLS、動的トークン、レート制限）を実装する必要がある。
2. **WAF の攻撃特徴マッチに完全文字列一致を使用してはならない**：`Mozilla/5.0 sqlmap` の検知漏れ、`<img onerror=>` の検知漏れ、UNION のコメントによる間隔挿入の検知漏れ――いずれも「防御しているように見えて実は防御できていない」事象である。
3. **WAF には header_anomaly が必須**：赤チームの 4 種類のルールには**UA ブラックリストが含まれていない**――あらゆるツールのフィンガープリントが侵入可能であり、UA を偽装するだけで簡単に回避できる。
4. **cmd_injection の単一文字ルールは落とし穴**：記述方法が誤っていると存在しないのと同じである。文脈（コマンドの後に `id` `whoami` `cat` などの関数名が続く）と組み合わせてパターンマッチを行う必要がある。
5. **LLM はアシスタントであり代替手段ではない**：flash モデルは初回成功したものの、その後 429/403 のレート制限が発生――本番環境では必ず「AI + 人手」の協働体制を構築し、LLM への攻撃の完全依存は避けるべきである。
6. **同一ソースコードには同一の脆弱性が存在する**：2 つのサービスの基礎 WAF コードはほぼ同一であった――これは両者が相手と同じ検知漏れを抱えており、ただ発火条件が異なるだけであることを意味する。実際の開発現場ではこれが「41 か所の脆弱性をコピーする」事象につながる。
