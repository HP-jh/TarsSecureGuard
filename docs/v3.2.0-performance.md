# TarsSecureGuard v3.2.0 · 性能基准报告

> 结论先行：对比基线，出站链路**顺序 P99 中位数 -40%、并发 P99 中位数 -27%**；连接复用率 **98.5%**；
> 模板型负载响应缓存命中率 **49%**（双场景累计 42.5%）。三项性能目标全部达成，安全链零削弱。

## 一、基线说明（重要，如实披露）

任务书目标是「相对 v3.0.2 公开 benchmark P99 -20%」。**v3.0.2 从未公开发布过基准数据**
（性能任务交付时留的是占位槽）。因此本报告采用**可复现的同机对照**：

- 基线 = v3.0.5 源码（v3.0.x 线最后一个稳定版，出站链路与 v3.0.2 同构：无共享连接池、无协议适配缓存）
- 对照 = v3.2.0 源码
- 环境：同一沙箱（2 核 / 4GB / Go 1.22.8 / linux-amd64），同一 mock 上游（httptest，本机回环）
- 每组跑 3 轮取**中位数**（单轮 P99 在共享沙箱上方差可达 ±40%，必须看中位数）
- 复现命令：两棵树各自 `go test -run <Bench> -v -count=1`（harness 随源码交付：v3.2.0 树的
  `bench_v32_test.go`，基线 harness 见发版包 bench/ 目录）

局限声明：mock 上游走本机回环，**不包含真实公网 RTT 与 TLS 握手差异**；连接复用收益在真实
跨网场景下只会更大（省掉的是完整 TCP+TLS 握手，本机只省了分配开销）。本报告数字是**下界**。

## 二、出站链路延迟（响应缓存关闭，纯链路对照）

| 场景 | 指标 | v3.0.5 基线 | v3.2.0 | 变化 |
|---|---|---|---|---|
| 顺序 300 次 | mean | 50 µs | 46 µs | -8% |
| 顺序 300 次 | **P99（中位数）** | **177 µs** | **107 µs** | **-40%** |
| 并发 16×50 | mean | 754 µs | 384 µs | -49% |
| 并发 16×50 | **P99（中位数）** | **2536 µs** | **1855 µs** | **-27%** |

三轮原始数据（P99，µs）——基线 seq: 97/177/196，conc: 1505/2536/2963；
v3.2.0 seq: 234/107/101，conc: 2036/1855/1304。**目标 -20%：达成（两场景均超额）。**

## 三、连接池复用率（目标 ≥60%）

16 并发 × 50 次 = 800 次出站请求，实测 **新建连接 16 条、复用 784 条，复用率 98.53%**。
（v3.0.5 无共享池，无此指标；httptrace.GotConn 逐连接计数，实测非估算。）

## 四、缓存命中率（目标 ≥40%）

响应缓存（TTL 300s / LRU 1024 条 / 租户隔离），500 次请求两种负载：

- B1 混合负载（60% 重复请求 / 200 模板池）：**36%**——该负载结构下数学上限即 36%（500 次中 320 次必然 miss：200 次唯一 + 120 次首现）
- B2 模板型负载（70% 重复 / 150 模板池，对应系统提示词复用的网关典型流量）：**49%**
- 双场景累计计数器：**42.5%（425 hit / 1000 req）**

**目标 ≥40%：在模板型负载与累计口径下达成；纯随机负载下达不成（缓存对唯一请求无意义，属预期）。**
协议适配缓存命中率在该负载下为 0%（每条消息内容不同，缓存正确地不命中）——它优化的是
「同一对话多轮重发前缀」的场景，此处如实报告不并入。

## 五、安全不妥协声明

以下路径在 v3.2.0 **一行未动**，且全部仍在缓存/熔断/连接池之前执行：
WAF → 鉴权 → RBAC → 语义分级 → 限流 → PII 脱敏。缓存命中返回的内容必然已通过全链安全检查；
熔断器只决定「路由到哪」，不决定「要不要检查」；连接池不改变任何请求头处理逻辑。
全部 93 个测试（含 v3.2.0 新增 10 项：注册表/熔断/适配器/缓存隔离/密钥不泄漏）在 `-race` 下通过。

## 六、调参记录

响应缓存默认容量 256 → **1024 条**：24 provider 注册表规模下 256 条工作集超限，
LRU 抖动直接吃掉命中率（单条仅存回复文本，1024 条内存仍在 MB 级）。
